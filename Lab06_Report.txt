1. FIFO vs LRU (Phase 2):
In the `page_replacement.py` script, why did the LRU algorithm perform better (have fewer page faults) than the FIFO algorithm for the given reference string? Explain how LRU decides which page to evict.

Ans: Based on the terminal execution output, FIFO resulted in 9 page faults (3 hits), whereas LRU produced only 7 page faults (5 hits).
- Why LRU performed better: The reference string contains frequent, repetitive requests for specific pages, notably Page 2 and Page 5. The LRU algorithm maintains a recency history; every time a page hit occurs, it treats that page as freshly used and updates its position so it stays in memory. On the other hand, FIFO blindly evicts pages based strictly on arrival time. When memory became full, FIFO evicted Page 2 simply because it arrived first, right before the program needed Page 2 again in the very next steps. This forced redundant re-loads and caused multiple consecutive page faults. In contrast, LRU preserved Page 2 and Page 5 by evicting older, unused pages (Page 3 and Page 1), yielding a streak of page hits near the end and keeping total faults down to 7.
- How LRU chooses the victim page: When a page fault occurs and the frames are full, LRU checks all pages currently in RAM and evicts the one that has not been referenced for the longest period of time. In the implementation, whenever a page hits, it is relocated to the end of the list (most recently used). Consequently, the element at index 0 is always the least recently accessed page and is chosen as the victim for replacement.

2. Understanding Thrashing (Phase 3):
Based on your observation of `ai_thrashing.py`, define "Thrashing" in your own words. Why is the processing time significantly higher in Scenario 2?

Ans: 
- Thrashing Definition: Thrashing is an overloaded state where an operating system spends virtually all its processing cycles moving data back and forth between physical RAM and disk swap storage rather than executing actual application logic, causing overall system throughput to collapse.
- Why processing time was significantly higher in Scenario 2: In the benchmark script, Scenario 1 took 0.5421 seconds, while Scenario 2 jumped to 1.4068 seconds (roughly 3 times slower).
  In Scenario 1, the data array fit entirely within physical RAM, allowing the CPU to read and update variables directly via fast memory buses in nanoseconds. In Scenario 2, simulating memory exhaustion forced the OS to persist updates to a disk file over 10,000 iterations. Because physical disk I/O latency is orders of magnitude slower than RAM access, the CPU spent most of its time blocked waiting for file reads and writes to complete (I/O wait), resulting in a severe performance drop.

3. AI Engineering Decision:
If you are training an AI model and your system begins to thrash because the RAM is full, lowering the `batch_size` in your Python code is a common solution. How does lowering the `batch_size` help the Operating System resolve the Thrashing problem?

Ans: The `batch_size` parameter determines the quantity of data samples and feature tensors loaded into memory concurrently during each training forward/backward pass. If `batch_size` is configured too high, the memory footprint required by input batches, model parameters, activations, and gradients exceeds the available physical RAM/VRAM capacity. This forces the operating system into aggressive page swapping, leading to severe thrashing.
Lowering the `batch_size` (for instance, reducing it from 128 to 32) directly solves this issue by shrinking the memory footprint of each training iteration so that it fits entirely within the physical RAM boundaries. Because memory is no longer overcommitted, the OS does not have to evict pages to disk swap. Page faults drop to near zero, eliminating disk I/O bottlenecks and allowing both CPU and GPU to train at native memory bandwidth.
